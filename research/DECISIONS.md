# Decisions log

Running log of what was decided during the research run and why. Newest last.

| # | Decision | Why |
| --- | --- | --- |
| D1 | Write research on a branch `research/coach-plan`, not on `main`. | CLAUDE.md git rules: one branch per piece of work, never commit straight to main. Only files under `research/` are added. |
| D2 | Treat `docs/SPEC.md` as the baseline and the new goal (coach that knows your playstyle, explains why, suggests new champions, growth, multi-user) as an extension of it. Where they differ, the research says so explicitly. | CLAUDE.md: "If a prompt conflicts with the spec, follow the spec and say so." The new goal mostly extends the spec; the differences are logged in ROADMAP.md as proposed spec changes for the owner to approve. |
| D3 | Keep the existing stack (TypeScript strict, pnpm monorepo, Electron + React + Vite, Zod, Vitest; Hono + SQLite planned). | The prompt requires building on the stack unless there's a strong reason; the codebase is clean and well tested, and nothing found justifies a rewrite. |
| D4 | Hosting: Railway Hobby stays the default; Oracle Cloud Always Free is the documented $0 fallback. Reject Render/Koyeb free (sleep or too small), Cloudflare (10 ms CPU), Fly (no free tier). | The collector must run 24/7 with a disk; Railway is zero-ops and already in the spec's $5 budget. |
| D5 | Meta data comes only from our own collector on the Riot API. No scraping; OP.GG's MCP only with written permission. | Only source that is clearly legal; personal-key capacity (~72k calls/day) covers one band (DATA_SOURCES.md §6). |
| D6 | Proposed spec/CLAUDE.md change (needs owner approval): allow **two** LCU write calls — create/replace a rune page and write an item set — only on an explicit user click, never during the pick/ban action itself, never touching champ select actions. Until approved, show runes/items with a copy-friendly layout only. | The spec promises "one-click import", but CLAUDE.md says the LCU client only does GETs. Rune import is standard in approved tools (it doesn't pick, ban or lock), so it fits "suggest, never decide" if user-initiated. Conflict flagged, not resolved silently. |
| D7 | In-game build advice uses Riot's official **Live Client Data API** (port 2999) instead of waiting for Overwolf. | Overwolf access is still pending; the Live Client Data API is official, free, and gives items/levels/scores for all champions — the inputs the spec's "armor when the enemy ADC is fed" example needs. Overwolf becomes optional (only for a true in-game overlay window). |
| D8 | Champion similarity features come from Riot's own game-data ratings (`playstyleInfo`, `tacticalInfo`, `championTagInfo`, `roles` via LCU / CommunityDragon) combined with measured stats from match data. | Spec forbids hand-labelled game data; these are Riot's data, per patch, not ours. Measured stats keep it honest when a champion is reworked. |
| D9 | Adopt DraftGap's Elo/log-odds maths for meta, matchup, counter and synergy factors (champion rating + deltas over expectation, smoothed toward expectation with prior games). Write our own implementation; cite DraftGap (MIT). | Transparent, additive (every term explainable), proven in a shipping tool, cheap to compute, fits the engine's pure-function style. ML models in the benchmark gave little extra and can't explain themselves. |
| D10 | Replace the Jev "confidence" in the UI with confidence derived from our own data (sample sizes + score gap): "Clear pick / Close call / Not enough data". Jev stays an optional adapter, not on the critical path. | Jev has no docs/key; the label is what players need, and we can compute an honest one. Spec deviation logged for owner approval. |
| D11 | Differentiate on (1) personalised + meta blend, (2) explanations from the factor breakdown, (3) growth plan with one focus at a time, (4) "we only ever look at you" privacy. Do not compete on lobby scouting, multi-game, or ML. | Market gaps found in Phase 3. |
| D12 | Engine v2 scores in additive rating points (log-odds) with terms meta / lane / counter / synergy / team / personal, each a delta over expectation; band weights kept in config. Replaces the weighted mean of 0–1 factors. | One scale → predicted win chance, "+2.3%" reasons and a meaningful "why not X". Checked against the spec: per-band weights in config survive; factor names map 1:1 (+ synergy). Counter-argument (more complex to read) answered by keeping 0–1 bars in the UI. |
| D13 | Playstyle = 8 named axes from percentiles of Match-V5 summary + `challenges` metrics vs a role-and-band reference; before the collector exists, the reference is lane opponents in the player's own games (anonymous). | Explainable ("top X%"), robust to skew, needs no new API calls (data already downloaded), compliant (aggregates only). |
| D14 | Situational runes/items are found by **lift** (pick-rate ratio when the enemy has trait T vs not) over collected matches, not by item lists. | Satisfies "never hardcode game data"; self-corrects after item reworks; produces a natural explanation. |
| D15 | Growth = one focus metric at a time, chosen by gap-to-band-median × measured importance in the band/role, on the main champion; target halfway to median. | Concrete and achievable; evidence-based; mirrors what a coach does. |
| D16 | New-champion recommender = cosine similarity on Riot ratings + measured traits, plus hole-filling, meta, ease, style match, minus overlap with mains. At most one "Learning" champion per role. | Explainable ("plays like your Viego"), uses only Riot/collector data, avoids pool bloat. |
| D17 | Engine runs on the desktop; the server ships hourly meta snapshots per band + per-user profiles + config. `POST /recommend` demoted to a debug endpoint. **Spec deviation — needs owner approval.** | Champ-select latency, works through server blips, ~zero server CPU (fits $5), the live draft never leaves the PC. Argued against: logic updates need app releases → mitigated by serving weights/templates from `/config`. Keys still never reach the client, which is the spec's actual requirement. |
| D18 | Multi-user via invite codes + Riot ID read from the logged-in League client + hashed bearer token; profile-icon challenge only when going public. | RSO needs a production key; friends are trusted; reading the Riot ID from the LCU avoids typos and casual impersonation. |
| D19 | New pure package `@ldc/meta` for aggregation; new `@ldc/live-client` adapter; `@ldc/jev` frozen; Overwolf deferred. | Same "pure core + adapters" rule as today; drop dependencies that block progress. |
| D20 | Installer via electron-builder (NSIS) + electron-updater on a public static location (public releases repo or Cloudflare R2), unsigned at first. | Private GitHub releases require a token in the client; signing costs money and is only needed if friends are put off by SmartScreen. |
| D21 | LLM wording: not in MVP; later opt-in with server-side key, spend cap, and number verification against template slots. | Templates are free and can't invent stats (spec); LLM is the first real cost (~$1–4 per user per month). |
| D22 | M5 collector (2026-10-05): no always-on process. A tiny Railway cron service (in `.railway/railway.ts`) wakes the server once an hour via an owner-token endpoint; the server collects for a bounded time inside the Riot rate limit (~450 matches/hour on a personal/dev key), recomputes aggregates in the pure `packages/meta`, publishes a snapshot per band, then goes idle and sleeps. Timelines (builds, skill order) wait for M6. League-V4 `entries/{queue}/{tier}/{division}?page=` returns `puuid` (summonerId is deprecated). | Keeps the service sleeping (~$0.50–2/month extra, est.); a volume can only attach to one service, so the collector must run inside the server process rather than as its own cron container. The dev key stops collection when it expires until `pnpm riot:key` runs. |
| D23 | Item ranking (2026-10-05, owner request): one pure `rankItems()` in `packages/engine` for the M6 loadout and M8 live advice. Inputs in game: **both teams' items**, threat per enemy (item gold + who killed you), allies' answer coverage, your gold and inventory. Ranked by **win added** at the moment of purchase (result − expected win for the game state then) plus situational lift from band + band above, never raw item win rate. Training data from Match-V5 timelines (M6), rebuilt into the same features the Live Client API shows (M8). Details in DESIGN.md "Item ranking". | Raw item win rate is biased by players who are already ahead (C1). Using the same features for training and play keeps the advice honest. Additive log-odds terms keep every suggestion explainable and fit the existing engine model. The original plan used only enemy items and ignored allies and your own gold. |
| D24 | Engine v2 tuning from the first backtest (2026-10-05, 742 collected Gold–Plat games, newest 25% held out; `pnpm --filter @ldc/server backtest`): team-needs strength `teamRatingScale` 40 → 10; smoothing priors stay 150 / 60. | Team needs is the only hand-set term. Log-loss got monotonically worse as it grew (0: 0.6930, 10: 0.6932, 40: 0.6947, 80: 0.6979; coin flip 0.6931), and at 317 games it alone was worse than a coin flip with a game-level 95% interval entirely above 0. Its reasons still show; it just no longer moves the win chance much. No other term or prior setting is distinguishable from a coin flip yet (expected: draft-only prediction is a weak signal and 556 training games is tiny); re-run the backtest after a few days of production collection (~10k games/day at 450/hour) before tuning more. |
| D25 | Comfort over meta, without one forced main (2026-10-05, owner): `personal.comfortScale` 80 → 160, `learningPenalty` 25 → 50, new `personal.fullComfort` 0.65 above which comfort adds nothing; role fit in engine v2 also accepts the band data (≥ `roles.minRoleSamples` games and ≥ `minRoleShare` in the role). | Owner: comfort on a champion matters more than picking the "right" champion, but the coach must not push one most-comfortable champion every game. So comfort is strong below the comfortable level (a never-played champion starts ~11 pts of win chance behind a comfortable one) and flat above it, letting meta, matchups and team needs choose among comfortable picks; a hard lane counter can still win. The role-fit fix stops a champion that clearly plays the role in the band from getting the off-meta penalty. |
| D26 | M5 scope at the merge (2026-10-05): the gold-at-15 half of the power curve moves to M6 (it needs match timelines, which M6 adds); per-role metric importance moves to M7 (only the growth focus uses it). Trends and power curves are shown as reasons only, not scored, until a backtest shows they add to the prediction. | Keeps M5 free of extra Riot calls per game (timelines cost one call each) and of features without a consumer yet; "information only" follows the evidence-first tuning of D24. |
| D27 | M6 builds (2026-10-06): the spec's `item_purchases` rows are **derived during the hourly aggregation** from compact, anonymised timelines stored with each collected match (gold per minute, item events, skill order), not kept as a separate table; builds and win added are published in the band snapshot (like `champion_stats` and `matchups`, which are snapshot parts too). The collector fetches the timeline for `collector.timelineShare` of games (1.0) and collects the band above for builds with `buildBandShare` (0.3) of the match and time budget; that band gets no snapshot of its own. | "Completed item" is derived from the current patch's Data Dragon, so rows rebuilt each hour stay right after item changes; a stored table would freeze the old definition. Same 15-minute wake-up, so no extra CPU or memory; about a third fewer games per hour; volume est. +$0.30/month (docs/CLOUD.md). |
| D28 | M6 item ranking in champ select: `rankItems()` scores each build slot by **win added** at that slot (rating points) plus Σ lift × how far the enemy team is above the band's average in the trait (magic, physical, frontline, engage, healing); candidates must be bought at that slot by ≥ `loadout.itemMinShare`; an item below `negativeGuard` win added is never #1. The core path shown is the ranked top item per slot; the most common path only when purchases are too few. Rune pages and spells are the best smoothed win rate among common options (≥ `minShare`); skill order and starting items are the most common choice. | Follows C1 (never raw item win rate) and D14 (lift finds answers from data). Draft-only intensity is what M6 can know; M8 adds both teams' live items with the same function. The item backtest (`pnpm --filter @ldc/server backtest`) reports top-1/top-3 hit rate vs "most bought" and win added when players agreed with our #1. |
| D29 | M6 import (D6 approved Oct 5): a separate `LcuImporter` is the only module that writes to the client: POST a rune page or PUT the page it created before (named "LDC: …"; it never deletes or edits the player's own pages), and PUT the item sets with one "LDC" set per champion (others kept). Only from the panel's Import buttons; `write()` refuses any other method or path; `config/app.v1.json` `import.enabled` switches it off remotely (it's in the served config). When every rune page slot is used, the player is asked to free one. | Keeps the "GET only" guarantee of `LcuHttp` auditable and gives the owner a kill switch without a release. |
| D30 | M6 item tuning from the first item backtest (2026-10-06, 397 local Gold–Diamond games with timelines, newest 25% held out, 1,653 purchases): `loadout.shareScale` 0 → 50 (what players commonly buy at a slot is the prior) and `builds.winAddedPriorGames` 30 → 300. With win added alone, top-1 was 48.3% vs 53.4% for "most bought" (top-3 64.4% both); with the prior, 53.3% / 64.4%. Win added of purchases that agreed with our #1 vs the rest was within noise in every setting (±~1.8 pts at this size). | Win added per item and slot is noisy until items have hundreds of purchases (C7); the prior stops noise from reordering common builds, and win added plus lift still move the ranking as evidence grows. Re-run `pnpm --filter @ldc/server backtest` after a few days of production collection (~7k games/day) before M8 ships live item advice (which must beat the plain core path). |
| D31 | M6 loadouts from few games (2026-10-06, owner: "show it with almost no data and say the samples are too short to be exact"): below `loadout.solidGames` (100) games a build is a **rough guide**: (1) partial pooling: your role's build plus the champion's other roles (spells stay role-specific); (2) your own games on the champion come first for runes and spells (≥ `personalMinGames`), and your most-finished items when the band has no purchases; (3) choose the most taken option, never the best win rate, and quote counts ("Most taken: 8 of 13 games") instead of win rates; (4) a note says where it came from. The snapshot now publishes builds from 3 games (`builds.minGames`), options from 1, item slots from 2. | Researched: stats sites show small-sample builds with their sample size (Lolalytics) and pick the most frequent build that beats the champion's average (U.GG); partial pooling is the standard fix for small groups; ranking by raw rate on tiny samples is the classic error (Wilson/Evan Miller). The owner's own games are often the biggest sample on their mains (89 Naafiri games vs 5 in the band) and fit "comfort first" (D25). |
| D32 | M6 items follow the lane (2026-10-06, owner: "a mid laner cannot take jungle items; suggest items by the lane and its matchup"): pooling across roles (D31) is limited to runes and skill order; starting items, item slots and the common path always come from your role (or your own games in it). The snapshot's `itemRoles` (share of each item's games per role, from data) keeps role-locked items in their role (`loadout.minItemRoleShare` 0.05). Your lane opponent counts `laneWeight` (2) times in the enemy traits, and when a lane matchup has ≥ `minMatchupGames` timeline games, its most taken start and a smoothed "finished first more often into X" lift on item 1 are used. | The first local test showed a jungle companion as Naafiri mid's start, pooled from her jungle games. Role-locked items are found from who buys them, so no item list is needed and new role items are handled after patches. |
